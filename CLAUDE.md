# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CineList is a collaborative movie-tracking PWA for a closed group of friends (Netflix-style catalog, ratings, stats, ranking). It is a **single-file vanilla JS/CSS/HTML app with no build step, no package manager, and no test suite** — `index.html` (~330KB) contains the entire app: all CSS in one `<style>` block and all JS in one `<script>` block. There is no `package.json`.

Backend is Supabase (Postgres + Auth), project ref `iznikddtdwfvkkwqtwxg` (i.e. `https://iznikddtdwfvkkwqtwxg.supabase.co`, matching `SUPA_URL2` in `index.html`). Hosting is GitHub Pages, deployed by pushing to `main` (auto-publishes; Fastly CDN in front has a ~10 min edge cache, so a just-pushed change may take a few minutes to show up live — verify with a cache-busted `curl` if it matters, not by re-pushing).

## Commands

There is no build/lint/test tooling — edit `index.html` directly.

- **Run locally**: serve the directory with any static file server, e.g. `python -m http.server 8080`, then open `http://localhost:8080`. The Service Worker and push notifications require HTTPS, so those specific features won't work over plain `http://localhost`.
- **Deploy**: `git push` to `main` — GitHub Pages serves directly from the repo root, no CI/build step.
- **Verify a change without a browser**: tables with an open `SELECT` policy (`filmes`, `avaliacoes`, `perfis`, `conquistas`, `compatibilidade`) can be queried directly via the REST API using the anon key already embedded in `index.html` (`SUPA_URL2`/`SUPA_KEY2`), e.g. `curl "$SUPA_URL2/rest/v1/filmes?select=id&limit=1" -H "apikey: $SUPA_KEY2"`. Useful for checking row counts or schema without waiting on the UI. `usuarios` requires an authenticated session (anon key alone returns nothing) and `fcm_tokens` has no public read policy either — both expected, not a bug.
- **DB export/backup**: `scripts/backup-console.js` is meant to be pasted into the browser DevTools console on the live, logged-in app (see `scripts/README.md`) — it reuses the page's already-authenticated Supabase client (`supa`) to dump all four tables to CSV, which sidesteps the `usuarios` RLS restriction. There is no Node-based equivalent in this environment/repo (no Node install was available when this was built; do not assume one exists).

## Architecture

### Data flow: `STATIC` seed → live Supabase overwrite

`index.html` embeds a `const STATIC = {...}` JSON blob (near the top of the main `<script>`) that seeds the initial in-memory state (`RAW.usuarios`, `RAW.users_stats`, etc.) before the network round-trip to Supabase completes. Historically this blob held full frozen snapshots of every derived stat, which caused real bugs (a stale "não quero assistir" list kept getting merged back in after being deleted from the DB; a login gate that trusted the frozen member list instead of a live query). Most of `STATIC`'s keys have since been emptied out — only `STATIC.usuarios` still carries real seed data, because `applyUserToUI()`/`buildUD()` synchronously read `USERS` (aliased to `RAW.usuarios`) during the very first paint after login, **before** the background fetch (`loadFilmsFromSupabase()` → `loadUsuariosFromSupabase()` → `calcUserStats()`) has resolved. Every other `RAW.*` key derived from `STATIC` (stats, highlights, monthly activity, per-user personal stats, available years/genres, recent-films list) is fully recomputed from live `FILMES`/`STATS` inside `calcUserStats()` on every load, so their `STATIC` seed values are inert placeholders (kept as `{}`/`[]` rather than removed, since other code reads `RAW.xxx` unconditionally).

If you ever need to hand-edit the `STATIC` line: it's one extremely long line (tens of KB), so `Read` with a line range will blow the tool's token cap — extract/patch it with `awk`/`sed`/PowerShell's `ConvertFrom-Json`/`ConvertTo-Json` instead of trying to view it directly. The file is UTF-8 without BOM, CRLF line endings — preserve both if you touch it outside the normal `Edit` tool.

### Global state (top of the main `<script>`)

- `RAW` — the mutable root object; most other globals are references into it.
- `USERS` = `RAW.usuarios` (keyed by `legacy_id`, e.g. `"USER-003"`), `STATS` = `RAW.users_stats` — both cleared and rebuilt wholesale by `loadUsuariosFromSupabase()` on every load (`Object.keys(...).forEach(delete)` then `Object.assign`), not merged.
- `FILMES` (array) / `FILMES_MAP` aliased as `FM` (object by id) — the catalog, populated by `loadFilmsFromSupabase()`.
- `CU` — the logged-in user's `legacy_id` (their "current user" key into `USERS`/`STATS`).
- `profileData` — keyed by `legacy_id`, sourced from the `perfis` table (apelido, bio, avatar, birthday, favorite film id) via `getProfile(uid)`.
- `supa` — the Supabase client (`window.supa`), created once at the top with the anon key; carries the authenticated session after login.

### Rendering

No framework — every view is a function that builds an HTML string and assigns it to `.innerHTML`. `render()` is the dispatcher that re-renders whichever top-level view (`CV`) is currently active (`renderHome`/`renderFilmes`/`renderPendentes`/`renderAvaliacoes`/`renderRecentes`/`renderRanking`/`renderDescobertas`). Film detail panels are duplicated per view (`#filmDetailPanel`, `#pendDetailPanel`, `#avDetailPanel`, `#recentDetailPanel`, plus a mobile full-screen modal `#mfmContent`) and each write action (rate, mark "não quero", add film) has to explicitly re-render whichever of these panels is currently showing the affected film — `render()` alone does not do this, since it may re-render a detail panel to a different film entirely. `displayName(uid)` and `avatarHTML(uid, opts)` are the shared helpers for showing a member's name/avatar with `perfis` apelido/photo fallback to `usuarios.nome`/generated color+initials — use these instead of reading `USERS[uid].nome` directly when adding a new place that shows a member.

The four `open*Panel(id)` functions (`openFilmeInPanel`/`openPendPanel`/`openAvPanel`/`openRecentPanel`, one per view above) each toggle row selection with `event?.currentTarget?.classList.add('selected')` — optional chaining on purpose, not a stray `?.`. A bare `event.currentTarget` throws when the function is called without a real click behind it (`event` resolves to `window.event`, `undefined` outside a handler) — caught during the deep-link-de-filme work (2026-08-25/26), which needed to call `openFilmeInPanel()` straight from the boot sequence, no click involved; fixed in all four at once rather than only the one the boot happened to touch. Copy this pattern, not a bare `event.currentTarget`, if a fifth view ever needs its own panel-open function.

Esc handler: a single global listener closes whatever overlay is open deepest-first (reused across every modal — the trilha modal was first to need it). A new overlay just adds a line to that one list; don't write a per-modal Esc listener.

**A view's sub-state must survive an unrelated `render()` call, or on-demand data loading will silently undo user navigation.** Any function that lazy-loads data (e.g. `loadComparativoParaUsuario()`) calls the generic `render()` on success to refresh whatever's on screen — but `render()` only knows about the top-level `CV`, not what's drilled into inside that view. Descobertas already got this right: `renderDescobertas()` re-reads `window.perfilSelecionadoUid` every time, so a stray `render()` just repaints the same profile. Ranking didn't, until a real bug proved it: clicking a member in the Ranking tab opened their profile, `userDetailHTML()` kicked off `loadComparativoParaUsuario(uid)` in the background (undefined comparativo cache), and when that fetch resolved — often within the same click-to-click window — its `render()` call ran `renderRanking()`, which rebuilt `#rankTabContent` back to the plain tab list with no memory that a profile had been opened. First click looked like it opened and instantly closed; the second click "worked" only because that uid's comparativo was cached by then, so no fetch and no clobbering `render()` fired. Fixed by giving Ranking the same pattern Descobertas already had: `rankDetailUid` (module-level) holds which profile is open in `#rankTabContent`, `renderRankTab()` checks it before falling back to the tab list, and both entry points that should exit the profile (`closeRankDetail()`, `setRankTab()`) explicitly clear it. **Known follow-up, not fixed**: the year-drilldown reachable from inside a profile (`openUserYearDetail`, clicking a year bar on someone's page) is a second layer of sub-state nested inside the first — if `loadComparativoParaUsuario`'s `render()` fires while that year view is open, `renderRankTab()` still redraws the *profile* underneath it (since `rankDetailUid` is untouched by entering the year view), clobbering the year view the same way the original bug clobbered the profile. Any future screen that adds on-demand data loading needs to ask this same question up front: does its sub-state survive a `render()` call it doesn't control?

**`supa.rpc()`/`supa.from()` builders are lazy thenables — they implement `then()` only, not `catch()` or `finally()`.** The actual HTTP request is built and sent inside `then()`; chaining `.catch(fn)` straight off a builder throws `TypeError: ...catch is not a function` synchronously, before any request goes out — not a rejected promise, a thrown error at the call site. For a fire-and-forget write, use `.then(({error}) => { if(error) console.warn(...); })`, or `await` it inside a function that already has its own `try/catch`. **Real incident, not theoretical**: `persistOmdbCache()`'s `supa.rpc('cache_omdb_rating', {...}).catch(()=>{})` never sent a single request — confirmed via `query_logs` showing zero real (non-curl) hits on `/rpc/cache_omdb_rating` in 24h, while the SQL function itself worked perfectly when called directly. The `.catch()` threw immediately, was swallowed by the enclosing `try/catch` in `fetchAndCacheOmdb()`, and the write silently never happened — for hours, undetected, because the in-memory `_omdbCache` had already been set one line earlier, so ratings kept displaying correctly and looked like everything worked. **Never write `.catch(()=>{})` (or any empty handler) on a fire-and-forget write** — an empty catch on a promise that DOES reject hides a real failure exactly the same way a `.catch()` that never even attaches (this bug) hides one; always log the error, never swallow it silently.

**Segundo bug na mesma função, achado pouco depois: falso positivo de match, não "not found".** Mesmo depois do fix acima e de um fix anterior de ordem de título (`original_title` primeiro, PT-BR reserva), `fetchAndCacheOmdb()` ainda buscava a OMDB por `t=titulo&y=ano` — e a OMDB não valida título, só casa por aproximação e aceita o ano como filtro estrito. A Lista de Schindler (`tmdb_id` 424) expôs isso: com `y=1993` (ano do catálogo) a OMDB retornava `Response:"True"` casado com "The Making of Schindler's List" (documentário de mesmo ano), cujos `imdbRating`/`Ratings`/`Awards` são todos "N/A" — o código só checava `Response==='True'`, sem validar título/imdbID, e gravava esses N/A como `null`, indistinguível de "não encontrado" na UI. Um levantamento nos 850 filmes com `tmdb_id` (catálogo × TMDB) achou 15 anos divergentes, mas checando a data mínima real de estreia (todo país/tipo) 13 eram legítimos (estreia em festival vs. lançamento amplo) — só 1 (`FILME-0064`, "Mate Ou Morra") ficou sem base, e mesmo esse acabou não sendo erro: IMDb diz 2020, TMDB/Rotten dizem 2021, e o catálogo bate com o IMDb, que é a base que a própria OMDB usa. Corrigido buscando por `imdb_id` (`i=tt...`, exato, sem título nem ano) em vez de título+ano: coluna `filmes.imdb_id` adicionada e populada pros 850 filmes com `tmdb_id` (2026-08-23), lida do banco ou, quando ausente, do campo `imdb_id` que a própria resposta de `/movie/{tmdb_id}` do TMDB já inclui de graça (mesma chamada que já buscava `original_title`) — só cai no fallback por título quando nenhuma das duas fontes tem `imdb_id` (hoje só o único filme do catálogo sem `tmdb_id`). Implementado e validado em 2026-08-23 (commit `71ac0ef`): A Lista de Schindler voltou a gravar nota real (9.0 IMDb, 98% RT, "Won 7 Oscars") com `imdb_id tt0108052`.

### Dates

Always build "today" as a local calendar date with `localDateStr(d)`, never `new Date().toISOString().split('T')[0]` — `toISOString()` is UTC and rolls over to the next day in the evening in Brazil (UTC-3), which previously caused `avaliacoes.data_avaliacao` to be off by one day. `toISOString()`/`Date.now()`-style values are still correct for genuine instants (`created_at`/`updated_at` timestamp columns, backup export filenames) — the distinction is calendar-date-as-seen-by-a-human vs. absolute-instant.

**Relative-day display ("Hoje"/"Ontem"/"X dias atrás") must diff local-midnight-truncated dates, never raw elapsed time divided by a day in ms.** `Math.floor((now - d) / 86400000)` only lands on the right bucket when `d` already happens to be anchored at local midnight (true for `data_avaliacao`/`data_cadastro`-derived dates, built via `new Date(y, m-1, d)` with no time component) — it silently breaks the moment `d` carries a real time-of-day, because a "day" measured from e.g. 22:14 doesn't align with actual midnight-to-midnight boundaries; the card shows "Hoje" for up to 24h from that timestamp instead of until the local calendar date actually rolls over. **Real incident (2026-09-01)**: an avaliação made 31/08 22:14 (Maceió, UTC-3) still showed "Hoje" in the feed the next morning — `feedGroup()`/`feedRelDate()` diffed `now` against `criadoEm` (`avaliacoes.created_at`, a real timestamp) with the raw-ms pattern. The timezone conversion (22:14 local → 01:14 UTC next day) made the bug easy to *notice*, but wasn't the cause — the same raw-ms bug would misfire even with zero UTC involved, purely from measuring "24 hours elapsed" instead of "did the local calendar date change." Fix: truncate both `now` and `d` to local midnight (`new Date(y, m, date)`, dropping time-of-day) before subtracting — `diasLocalAtras()` does this once, shared by both callers. Same principle as `localDateStr()` above (calendar-date-as-seen-by-a-human vs. absolute-instant), applied to *differences* instead of a single "today" value.

|---|---|---|
| `usuarios` | `legacy_id` (text PK, e.g. `USER-003`) | Membership list. SELECT requires an authenticated session (anon key alone returns nothing). `in_ranking` (bool) controls ranking inclusion, and triggers two downstream recalcs — see Conquistas and Compatibilidade. A DB trigger auto-generates the next sequential `legacy_id` (`USER-NNN`) when a new row is inserted with that field left empty — the admin "criar membro" flow relies on this and only sends `legacy_id` explicitly when overriding it. A separate DB trigger links a Supabase Auth account to a row here by matching email, in either direction (account created before or after the row). |
| `perfis` | `legacy_id` (text PK, FK → `usuarios.legacy_id`) | Optional per-user profile: `apelido`, `bio`, `bday` (date; unknown year is stored as `1900`, not `0000` — Postgres doesn't accept year 0), `fav_filme` (stores a `filmes.id`, not a name — resolve via the in-memory `FM` map and treat a missing/stale id as "no favorite" rather than erroring), `fav_genre`, `avatar_color`, `avatar_url` (a data: URI — photos are resized client-side to 256×256 JPEG before upload). `SELECT` open to everyone (`read_all`); writes are three policies scoped `TO authenticated` (`perfil_insert`/`perfil_update`/`perfil_delete`), each restricted to the owning row via `legacy_id = (select usuarios.legacy_id from usuarios where usuarios.auth_id = (select auth.uid()))`. |
| `filmes` | `id` (text/uuid, mixed formats) | `id` has two historical formats — `FILME-0211`-style strings from an old migration and UUIDs for everything added since — never assume one or the other. Unique on `(lower(btrim(nome)), coalesce(ano,''))`; a duplicate insert raises Postgres error `23505`, which the UI should catch and show a friendly message for, never the raw driver error. `ano` is `text`, not an integer — compare it as a string (or normalize both sides) rather than `parseInt`ing one side only. `tmdb_id` (int, unique partial index — allows null) is populated on insert from the TMDB search step; 840/841 films have it, the one holdout being a non-standard "saga completa" catalog entry. |
| `avaliacoes` | `(filme_id, usuario_id)` composite | One row per user per film they've rated *or* marked "não quero assistir" (`nota IS NULL` + `vai_assistir='Não'` is the marker for the latter — there's no separate table for it). Writes are `upsert`s with `onConflict: 'filme_id,usuario_id'`. `data_avaliacao` (text) has two live formats today — empty string and ISO `YYYY-MM-DD` (the historical BR `DD/MM/YYYY` format was normalized away 2026-08-28, see item 10 in Pendências) — never compare/sort it as a raw string without accounting for empty. **1.085 rows** (2026-09-05, down from 1.293 — active manual recovery in progress, see "Recuperação de datas antigas" below) have `nota` set but empty `data_avaliacao` — real ratings that lost their date during an AppSheet migration (`created_at` on the still-undated ones is uniformly `2026-04-05 03:13:39`, the migration instant, not a real timestamp), not "old" data (dated rows go back to 2023), so the UI must say "data não registrada" for whatever's still missing, never guess a date or era. |

| `compatibilidade` | `(a, b)` composite, `a < b` always | State, not history — one row per pair of `in_ranking=true` usuários, fully overwritten on every recalc. | `fcm_tokens` | `email` | Push notification device tokens; unrelated to `usuarios.legacy_id`, keyed by email directly. |

### Conquistas (achievement trilhas)

`conquistas` records, once and permanently, the moment each member crosses each tier of an achievement trilha (Volume, Curadoria, Pioneirismo, Maratona Mensal, Tempo na Tela, Diversidade de Gêneros, Viajante do Tempo, Filmes Longos, Consistência, Influência). It's populated by replaying `avaliacoes`/`filmes` per user — not something `index.html` computes; there is no client-side "conquistas" calculation.

**Trilha vs. especial — not the same nature, and it's easy to trip on this**: a **trilha** is história — frozen, never revoked, has a date, lives in `conquistas`. A **especial** is *estado* — recalculated live from current data every render, can be lost if the underlying condition stops holding (e.g. the tropa's average for a film shifts and a Defensor case no longer qualifies), and has no achievement date because there isn't one to have. Especiais are never written to `conquistas` — same nature as `compatibilidade`, which is also *estado*. **The UI must never notify or show a delta when a especial is gained or lost** — same rule as compatibilidade, opposite of a trilha tier.

**Especiais set (current, 7): Otimista, Crítico, Fã de \<gênero favorito da pessoa\>, Apaixonado, Defensor, Estraga-Prazeres, Termômetro.** Computed live off the Fase 3 views (Defensor/Estraga-Prazeres/Termômetro — see Base de comparação) or off `RAW.users_stats`/`FILMES` directly (the other four), same pattern as compatibilidade. "Fã de \<gênero\>" is dynamic per person (40%+ of their filmes in their own `fav_genre`) — not hardcoded to one genre. **Apaixonado** (3+ notas 10) is what survives of an older multi-tier "Notas 10" ladder: the tiers past the first rewarded rating inflation (someone who rates with real judgment never gets there), but "gave a 10 at least a few times" is a real trait, so only the binary first tier survives. **Retired, do not reintroduce**: Bom Humor (duplicated Otimista's axis), Difícil de Agradar (duplicated Crítico's axis), Implacável (required five notas 0, which nobody in the tropa has — a especial that zeros isn't a especial, same calibration rule as below). Voz Dissonante stays cut — see Base de comparação for why and the revisit idea.

**Selo nunca revogado**: once a `(usuario_id, trilha, tier)` row exists, no normal run ever updates or deletes it — every insert (backfill or incremental) uses `on conflict (usuario_id, trilha, tier) do nothing`. This holds even when the underlying condition later stops being true — Pioneirismo can lose its condition the moment someone else rates a "solo" film, and **a duplicate-film merge can retroactively lower any counter** — but the achievement date/precision already on record must never change.

**Correction model**: because of the above, deleting rows and re-running is only safe while a `versao_backfill` tag is still a genuine test tag (see below). Once a tag is promoted, fixing bad data is an incremental replay — the same insert, same `on conflict do nothing` — never `delete` + re-run, since a delete would let the next run silently mint a *different* date for an achievement someone already experienced.

**`versao_backfill`** means *origin of the row*, not "which backfill execution" — the two values in use are permanent, not test tags to eventually clean up. `v1` = the one-time historical backfill (196 rows). `gatilho` = every row inserted automatically, forever, by the triggers below — the same tag on every firing, not a per-execution id. **Do not delete `gatilho` rows as if they were leftover test data** — they're real achievements dated the day the trigger caught them. The "wipe while under test" pattern (`delete from conquistas where versao_backfill = '<tag>'`) only applies to genuine one-off test tags (e.g. `'incremental-teste'`) — never to `v1` or `gatilho`.

**Replay incremental**: `recalcular_conquistas(p_versao_backfill text default 'incremental')` is a `SECURITY DEFINER` SQL function (needed since `conquistas` has no insert policy for anon/authenticated) that recomputes all 10 trilhas' live values for every usuário and inserts any newly-crossed tier with `data=current_date`, `precisao='exata'` — an incremental crossing is always dated in real time; `indeterminada` only ever applies to the frozen historical batch, never to anything the trigger inserts. Two triggers call it, both `FOR EACH STATEMENT` (fires once per command, not once per row — a future bulk import in one multi-row `INSERT` only recomputes once; if a bulk job ever needs many separate single-row statements instead, disable the trigger for that operation with `alter table <tabela> disable trigger <nome>` and re-enable after):
- `avaliacoes_recalcula_conquistas` (AFTER INSERT OR UPDATE on `avaliacoes`)
- `filmes_recalcula_conquistas` (AFTER INSERT on `filmes`) — needed separately because adding a filme without rating it is a real, common flow (the add-film UI defers rating with an "avalie agora 👇" prompt, per `index.html:2292`), and Curadoria's counter depends only on the insert, never on an avaliação.

Full recompute (every usuário, not scoped to just the writer) is deliberate: Influência credits the *inserter* of a filme when *someone else's* rating pushes it past the approval threshold, so a trigger scoped to "recompute only whoever just wrote" would never light up Influência for anyone. The one trilha where writer-scoping would work (Pioneirismo) is harmless the other way too — a third party's rating can only ever lower someone else's *live* Pioneirismo count, never cross them a new tier, and a dropped live value never revokes a recorded selo. Measured cost of a full recompute across every usuário: **~53ms**, paid once by whichever transaction triggered it.

**`precisao='indeterminada'`** (with `data=null`) marks a tier crossed while replaying the ~1,293-row undated migration batch in `avaliacoes` (see the schema table above). Only Volume, Tempo na Tela, Diversidade, Viajante do Tempo and Filmes Longos can land there. **The indeterminada case must never say "antes de 2025" or guess a year** — dated `avaliacoes` rows go back to 2023, and the undated rows just lost their registro, not necessarily old. Maratona Mensal and Consistência already exclude undated rows from their own counters entirely (an older, unrelated decision — see the "avaliações sem data" warnings surfaced in the Conquistas/Ranking UI); Curadoria always has a `created_at` fallback so it's never indeterminate; Pioneirismo and Influência depend on *other* members' dated activity so they essentially never land in the undated block either.

**Degraus infinitos (trilhas sem teto)**: Volume, Curadoria, Pioneirismo, Maratona Mensal, Tempo na Tela, Filmes Longos, Consistência and Influência have no ceiling — past the last named tier, more are generated up to 12 total per trilha (named + synthetic) using

```
passo   = max(5, 5 * 10^(dígitos(limiar) - 2))
próximo = ceil(limiar * 1.3 / passo) * passo
```

(`dígitos(x)` = number of digits in `floor(x)` — this proportional step, not a flat `/25`, is what keeps the ladder sane at both small scale, e.g. Consistência's 24→35→50→65→85, and large, e.g. Volume's 900→1200→2000→3000). The synthetic tier's name is the last named tier's selo plus a roman numeral (`Divindade II`, `Divindade III`, ...), except Tempo na Tela, whose synthetic name is just the value with a pt-BR thousand separator (`1.500 Horas`). Diversidade de Gêneros and Viajante do Tempo are capped ("teto") trilhas and never get synthetic tiers.

**Catálogo canônico de degraus** — this table is the single source of truth for every named tier. `index.html` must define this catalog in exactly one place (a single array/object), consumed both by the live "current value + progress to next tier" calculation and by any future replay/backfill tooling — two lists is what caused an earlier drift between the client-side ladder and the DB backfill.

### Base de comparação com a tropa

Two views feed both the compatibility formula and the leave-one-out especiais below. Both are plain (non-materialized) views — the dataset is small enough (841 filmes, `in_ranking` usuários) to recompute live, so no refresh strategy is needed. Both scope to `nota is not null` and `usuarios.in_ranking = true`; dated and undated `avaliacoes` rows are both included (excluding undated rows would drop 38% of the base — see the `avaliacoes` schema row above). Both use `security_invoker=true` — see Segurança below.

- **`v_filme_stats`** — per-filme `n_avaliacoes`, `media_tropa` (full population), `variancia` (`var_pop`, not `var_samp` — `var_samp` doubles the variance at n=2, which would inflate exactly the small samples that should carry the least weight), `peso` (`variancia / média_da_variância_dos_filmes_com_n≥2`, clamped to `[0.25, 2.2]`). Filmes with `n_avaliacoes = 1` are excluded entirely — a film only one person rated can never be a "filme em comum" between two people, so including it only pollutes the peso distribution (it would always sit at the floor).
- **`v_avaliacao_comparativo`** — one row per avaliação, with three distinctly-named means so they never get swapped: `media_pessoa`/`desvio_pessoal` (that person's own average across their own avaliações — feeds the Pearson correlation in Compatibilidade), `media_tropa`/`desvio_tropa` (the full-population average from `v_filme_stats` — feeds peso/compatibilidade, never leave-one-out), and `media_tropa_sem_ele`/`desvio_tropa_sem_ele`/`n_outros` (leave-one-out, excludes the person's own nota — feeds only the especiais below, never compatibilidade).

**Regra de método**: leave-one-out vale para todo selo/especial que compara uma pessoa contra a tropa — sem isso a pessoa competiria contra a própria contribuição (com n=4, uma nota isolada já é 25% da média). NÃO vale para peso/compatibilidade — ali a variância é propriedade do filme, não de quem está sendo comparado.

**Regra de calibração** (vale pra estes especiais e pra qualquer especial futuro): alvo de 1 a 4 pessoas por especial num grupo pequeno (calibrado com 14 `in_ranking` — o que importa é ficar raro, não o número exato). Especial que zera não existe; especial que 11 de 14 têm não é conquista, é comportamento normal da base.

**Especiais calibrados sob essa regra** (todos leave-one-out, `n_outros ≥ 4`, i.e. 5 avaliações no total — a mediana de avaliações por filme na base é 4, então esse piso é o "normal" da base, não um corte artificialmente apertado):
- **Defensor** — `media_tropa_sem_ele < 6.5` e `nota ≥ 8`.
- **Estraga-Prazeres** — `media_tropa_sem_ele > 8.2` e `nota ≤ 6`. `nota ≤ 6` foi calibrado, não escolhido: com `≤ 5` (o corte simétrico "óbvio" ao 8+ do Defensor) dava 1 caso em 1 pessoa — a tropa avalia alto demais para "dar 5 num filme amado" acontecer.
- **Termômetro** — 60%+ das avaliações elegíveis a menos de 0,5 de `media_tropa_sem_ele`, piso de 50 filmes elegíveis (`n_outros ≥ 4`). 60% também foi calibrado: com tolerância de 0,5 mas sem corte proporcional (contagem absoluta), 11 de 14 pessoas ganhavam — o selo saturava, porque a tropa concorda demais para "estar perto da média" ser incomum.

6.5 ("tropa afundou") e 8.2 ("tropa amou") são estatisticamente simétricos — mesma fração de filmes (11,5%) de cada lado da distribuição de `media_tropa` — não valores redondos escolhidos à mão.

**Voz Dissonante — cortado, não faz parte do set atual.** O critério original (10 filmes a 3+ pontos da média) dá zero pessoas: a tropa concorda demais para "discordar muito" acontecer 10 vezes com distância bruta. Um corte proporcional (15%+ das avaliações a 2+ pontos, piso de 50) também zera; forçar pra baixo (5%) só captura "discordar de 1 filme em 20", que numa tropa homogênea é ruído, não característica de personalidade. **Ideia a revisitar**: usar o `peso` de variância de `v_filme_stats` — discordar especificamente nos filmes que racharam a tropa (peso alto), não distância bruta da média num grupo que raramente racha.

### Compatibilidade

Compatibility score between pairs of `in_ranking=true` usuários, stored in `compatibilidade` as *estado* — fully overwritten on every recalc, no history, same nature as especiais and for the same reason: it can legitimately go up or down as anyone rates anything, and the UI must never show a delta or notify on change.

**Fórmula (v2, tag `versao_formula = 'v2'`)**: weighted Pearson correlation over `desvio_pessoal` (from `v_avaliacao_comparativo`) on filmes em comum between a pair, weighted by `peso` (from `v_filme_stats` — peso is a property of the filme, not of who's being compared). `r_bruto = Σ(peso·da·db) / √(Σ(peso·da²)·Σ(peso·db²))`, clamped to `[-1, 1]` to absorb float rounding at the edges (matters mainly at `n_comum=1`, where the raw ratio is always exactly ±1 by construction and can briefly round past it). Sample-size brake: `r_ajustado = (n/(n+K))·r_bruto + (K/(n+K))·r_grupo`, `K=15`, `r_grupo` = average `r_bruto` across all pairs with data in that run (stored per-row in `media_grupo` for audit, even though it's the same value for every pair in a given run). Display: `pct = round(50 + 50·r_ajustado)`.

This replaced an older client-side formula (raw shared-film note-difference, minimum 3 filmes em comum) that was imprecise at the top of its range and treated raw note distance as agreement even when two people were just equally generous — exactly what `desvio_pessoal` fixes. `K=15` was validated against the brake's actual behavior — a genuinely high `r_bruto` from a small sample still lands near its raw value (e.g. `n_comum=1` around pct 72, not shoved to the group average); the brake stops small samples from *outranking* large well-supported ones, not from mattering at all — and isn't being recalibrated without new evidence. A faixa de `pct` de qualquer execução é retrato daquele momento, não propriedade da fórmula — ela muda sozinha quando entra ou sai membro, então um mínimo mais baixo numa sessão futura não é regressão.

`recalcular_compatibilidade(p_versao_formula text)` upserts every `in_ranking` pair by `(a,b)`, recomputing membership (`select legacy_id from usuarios where in_ranking = true`) from scratch on every call — so it always produces the full current cartesian product, not just pairs already in the table. **Pairs with zero filmes em comum get `n_comum=0` and `pct = NULL`**, never collapsed to `r_grupo` — a number with no basis is worse than no number; the UI reads `pct is null` as "ainda não dá pra comparar."

**`n_comum >= 15` é o limiar de confiabilidade** (distinto de `pct = NULL`, que é limiar de existência — zero filmes em comum). O corte reusa o próprio `K=15` da fórmula, não é um número novo: o peso do sinal real em `r_ajustado` é `n/(n+K)`, que só ultrapassa 50% quando `n >= K` — abaixo disso, mais da metade do número é a média do grupo, não o gosto da pessoa. Pares abaixo do limiar são *estado próprio* na UI (ex. "ainda conhecendo o gosto de {Nome}" — número presente mas apagado, sem cor de faixa, ordenado por último), nunca escondidos ou tratados como afinidade baixa de verdade.

**Disparo do recálculo: gatilho em `usuarios` + `pg_cron` diário, não só manual.** Dois problemas de natureza diferente motivam os dois mecanismos. Um membro novo (`in_ranking` passa a `true`) fica sem nenhuma linha em `compatibilidade` até alguém rodar a função de novo — isso é *existência*, resolvido por dois gatilhos `AFTER INSERT/UPDATE FOR EACH ROW` em `usuarios` (`usuarios_entra_ranking_recalcula_compat`, `usuarios_promovido_ranking_recalcula_compat`, condicionados a `in_ranking=true`) chamando a função wrapper `_trg_recalcular_compatibilidade()`. Isso não cobre a *deriva* de alguém que já existe e segue avaliando — o gatilho só dispara em mudança de `in_ranking`, não em cada avaliação nova. Por isso também um `pg_cron` diário (`recalcula_compatibilidade_diario`, 07:00 UTC = 04:00 Brasília — `cron.timezone` do projeto é GMT, e o Brasil não tem horário de verão desde 2019, sem variação sazonal a corrigir) rodando `recalcular_compatibilidade('v2')`. Rejeitado: disparo no carregamento do app por idade do `calculado_em` — exigiria abrir `EXECUTE` da função pra `authenticated`, contra ganho quase nulo num grupo de ~15 pessoas com recálculo de ~132ms.

**Nota sobre pg_cron especificamente, pra não confundir uma sessão futura**: a extensão foi vetada explicitamente numa fase anterior, quando a fórmula de compatibilidade ainda estava sendo calibrada — um job automático rodando contra um `K` ainda em teste era o problema, não o pg_cron em si. Esse motivo caducou com `v2` promovido e validado; o veto foi levantado pelo próprio usuário depois disso, e só então a extensão foi ativada de propósito. Se `pg_cron` aparecer ativo depois de ter sido vetado numa sessão anterior, não é drift — é uma decisão revisitada e revertida depois que a condição que a motivava deixou de existir.

**UI: três estados via `compatEstado()`, não binário null/not-null**: `sem_dado` (`n_comum=0`) não mostra número algum. `normal` (`n_comum>=15`) mostra o `pct` real com cor, calibrada pra faixa real de v2 (não as faixas 80/60/40 da fórmula antiga, que deixariam quase todo mundo amarelo). `baixo` (`n_comum` 1–14) mostra **`n_comum/15` como progresso, não como percentual**, muted, sem cor de faixa, mais uma barra de progresso fina e "ainda conhecendo o gosto de {Nome}" — um `%` real foi tentado primeiro e descartado: com `n_comum=12` e `K=15`, só 44% do peso de `r_ajustado` é sinal real, o resto é a média do grupo, e um `%` muted ainda não resolve isso, porque o número é lido antes de a muting ser percebida. O "ver detalhes" expandível por par mantém seu próprio cálculo por filme ao vivo — `compatibilidade` só guarda o agregado, nunca "quais filmes". Mostra só fatos sobre filmes específicos (nota máxima em comum, ambos amaram, maior divergência, só vocês dois assistiram, "{Nome} amou e você não viu"), pra todo estado — um fato sobre N filmes compartilhados é verdade independente da confiança no agregado. Blocos que resumiam isso num percentual agregado (afinidade por gênero, evolução da afinidade, gênero divisor, ano médio, "X generoso/crítico") saíram em 2026-08-25 — repetiam o `pct` do topo do card, só fatiado, sem ajudar ninguém a decidir o que assistir (ver Pendências conhecidas).

**Inconsistência do item 15 fechada (2026-08-25)**: os blocos que convertiam diferença bruta de nota num "score %" comparável ao `pct` do placar (afinidade por gênero, evolução da afinidade) saíram do painel "Ver detalhes" junto com a limpeza acima. `calcAfin()` ainda usa diferença bruta de nota internamente pra uma coisa só — escolher qual filme destacar em "Maior divergência" (`Math.abs(notaA - notaB)`) — mas isso exibe as duas notas cruas lado a lado como fato pontual sobre um filme específico, nunca um percentual de afinidade concorrendo com o `pct` v2. Não é mais a mesma classe de inconsistência que motivava o item: não sobrou nenhum segundo "score" no detalhe pra contradizer o placar.

### Recomendações ("Pra você")

Duas listas na aba Descobertas › Pra você, fontes e fórmulas diferentes, mesmo princípio de freio de amostra.

- **Bloco A — "Do CineList, pra você"** (`computeCineListParaVoce()`): filmes do próprio catálogo que o usuário ainda não avaliou nem recusou (`STATS[uid].pendentes`, que já exclui `nao_quer`), ranqueados pela média das notas de quem já avaliou, ponderada pela compatibilidade real (`getCompat()`, tabela `compatibilidade`) — quem não tem par de compatibilidade conhecida não contribui peso nenhum, nunca vira um neutro 50. Zero chamada externa: `RAW.compatibilidade`/`FILMES`/`STATS` já estão na memória do cliente, recalculado a cada abertura da aba, sem cache. Corte em 20.
- **Bloco B — "Fora do CineList"** (`computeRecommendations()`): agrega `/movie/{id}/recommendations` do TMDB pros 20 filmes mais bem avaliados do usuário, excluindo qualquer filme já no catálogo (avaliado ou não — o Bloco A é dono desse território, o mesmo filme nos dois seria confuso). Ranqueado por `vote_average` do TMDB. Cache em `localStorage`, corte em 30 (mais que o Bloco A de propósito: filme de fora não dá pra avaliar sem adicionar primeiro, então vale ter mais opção pra escolher).

**Freio de amostra, mesmo princípio nos dois blocos, `k` diferente por bloco**: `nota_final = (n/(n+k))·nota_base + (k/(n+k))·média_de_referência` — mesmo princípio do `r_ajustado` da fórmula de compatibilidade acima. `n` é sempre a contagem de avaliações que embasam a `nota_base` (raters com `pct` conhecido no Bloco A, `vote_count` no Bloco B) — nunca uma contagem bruta que possa divergir da base real do cálculo. **Bloco A usa `k=3` fixo**: o catálogo tem muito lançamento recente com poucas notas por natureza, e um `k` maior puniria demais esses; aqui `n` é o número de PESSOAS da tropa que avaliaram (máximo ~14), então `k=3` já é proporcionalmente pesado. **Bloco B usa `k` = mediana do `vote_count` dos próprios candidatos elegíveis daquela lista, calculada na hora** (não um número fixo) — porque `n` aqui é o `vote_count` do TMDB, de escala completamente diferente: dezenas a dezenas de milhares, não pessoas. Um `k=3` fixo nessa escala deixava o freio inerte — um filme com 46 votos mantinha ~94% do peso da própria nota crua (`46/(46+3)`), o mesmo problema de ruído no topo que o freio existe pra resolver (ver "Motivação real do freio" abaixo). **Confirmado com dados reais (2026-08-27)**, lista de recomendações de um usuário: mediana do pool = 610 votos. Com `k=3`, "Jesus - A Luz do Mundo" (47 votos, nota 8.69) ficava em 1º e "Eu Só Posso Imaginar 2" (46 votos) em 4º — ambos com lastro mínimo. Com `k=mediana`, os dois saem do top 10 e entram "Jojo Rabbit" (10.623 votos) e "A Doce Vida" (2.063 votos), consagrados de verdade.

A `média_de_referência` **nunca é a mesma nos dois blocos, e nunca é um número fixo no código** — escalas diferentes (nota da tropa 0-10 subjetiva vs. `vote_average` público do TMDB) tornariam qualquer constante compartilhada ou hardcoded uma "constante mágica" que ninguém entenderia depois: Bloco A usa a média geral de toda nota já dada por qualquer um da tropa (`mediaGeralTropa()`, só `in_ranking=true`, calculada na hora); Bloco B usa a média de `vote_average` **dos próprios candidatos elegíveis daquela lista**, calculada na hora — nunca a média da tropa.

**Motivação real do freio (2026-08-23)**: ordenar por nota crua (Bloco A) ou por frequência de recomendação (`count`, versão anterior do Bloco B) deixava ruído no topo — um filme com 1 nota 10 batia dez filmes com média 8,5, e no levantamento real do Bloco B 256 de 271 filmes empatavam em `count=1` (94%), ordem praticamente aleatória; sem piso de `vote_count`, "Jesus - A Luz do Mundo" (46 votos, nota 8.66) subia na frente de "Os Bons Companheiros" (14.656 votos, nota 8.45). Com o freio: "Toy Story 5" (1 nota, 10.00) caiu de 1º pra 3º (8.11 ajustado); "O Rei Leão" (10 notas, 8.52) subiu de 8º pra 2º — validado com dados reais de um usuário.

**Ajuste por gênero e por década, testados e descartados (2026-08-23) — não refazer sem motivo novo**: sinal real existe nas pontas (Guerra +0,59, Terror −0,64 de desvio médio; Animação recusada 6x mais que assistida), mas some quando o filme tem 3-4 gêneros (maioria do catálogo) e se tira a média dos ajustes — na simulação, quase todo ajuste final ficou entre −0,1 e +0,1, imperceptível. Ajuste por década não tem sinal nenhum: as quatro décadas testadas ficaram entre 7,31 e 7,57 de nota média, sem diferença que justifique pesar.

**Cache do Bloco B** (`localStorage`, chave `cinelist_recs_<uid>`) invalida por `versaoFormula` (sobe a cada mudança na fórmula — sem isso, mudar a lógica não invalidava cache velho, causou um "mostra 276 itens sem corte em vez de 20" real numa sessão de teste), 30 dias, 10+ avaliações novas desde o último cálculo, ou clique manual em "Atualizar". `RAW._paraVoceForaEmCalculo` (Set por uid, mesmo padrão de `RAW._comparativoEmCarregamento`) impede um 2º cálculo disparar em cima de um 1º ainda em voo — podia acontecer avaliando um filme do Bloco A enquanto o Bloco B ainda calculava, duplicando até 20 chamadas TMDB e arriscando o que terminasse por último sobrescrever o cache com resultado de um estado já ultrapassado.

**Ações diretas nos cards, sem sair da lista (2026-08-23)**: Bloco A tem "⭐ Avaliar" (`openRate()`, já genérico, sem mudança) e "🔖 Quero ver" (`marcarQueroVer()` — upsert direto em `avaliacoes` com `nota:null, vai_assistir:'Sim'`, sem abrir modal, mesmo padrão do `mudarDeOpiniao()`; `data_avaliacao`/`comentario` ficam de fora do upsert, nunca gravados como string vazia — esse valor tem significado histórico específico, ver a linha de `avaliacoes` no schema acima). Bloco B tem "➕ Adicionar" (`adicionarDoBlocoB()` → `enrichTMDBResult({tmdbId})` direto, pula a busca por nome já que o `tmdb_id` é conhecido) com **confirmação de dois toques no próprio botão** (1º toque arma "Confirmar?", 2º confirma, ~3s sem confirmar desarma sozinho — sem modal, sem `confirm()` nativo; estado (`blocoBArmado`) fica fora do HTML porque o card é reconstruído a cada `render()`). Núcleo de inserção (`inserirFilmeDoTmdb()`) compartilhado com o modal normal de adicionar (`saveFilme()`), incluindo o patch cirúrgico do cache do Bloco B (`removerDoCacheParaVoce()`) que tira o filme recém-adicionado da lista de "fora do CineList" sem invalidar o cache inteiro. **Adicionar pelo card dispara `enviarNotifFilme()`, igual ao modal.** Nasceu sem notificar (2026-08-23), sob o argumento de que um clique de card — bem mais frequente que o fluxo de busca do modal — viraria spam e arriscaria alguém desligar push de vez. Revertido em 2026-08-24 por reclamação real da tropa: sem notificação o filme ficava invisível até alguém tropeçar nele, e o motivo original não se sustentou na prática — era hipotético, e a confirmação de dois toques do próprio botão já segura o clique acidental, que era o risco real por trás do argumento do spam.

### Segurança: SECURITY DEFINER e RPC pública

**Regra**: toda função `SECURITY DEFINER` nasce exposta via RPC. A anon key é pública — embutida em `index.html`, servida estática pelo GitHub Pages, visível a qualquer um que abra o site — então por padrão Postgres/PostgREST deixam `EXECUTE` liberado pra `public` (que inclui `anon` e `authenticated`) em toda função nova. Numa função comum isso é inofensivo porque a RLS da tabela ainda barra a escrita; numa `SECURITY DEFINER` (que existe justamente pra *contornar* a RLS de uma tabela sem policy de escrita, como `conquistas` e `compatibilidade`) isso reabre exatamente o buraco que a função foi criada pra evitar de outro jeito. **Fechar o `EXECUTE` é parte de criar a função, não um passo de segurança separado pra lembrar depois** — mas o fechamento certo depende de quem legitimamente precisa chamar:

- **Só gatilho/cron chama, nunca o cliente** (ex. `recalcular_compatibilidade()`, `_trg_recalcular_compatibilidade()`) — revoga de todo mundo:
```sql
revoke execute on function public.<nome>(<args>) from public, anon, authenticated;
alter function public.<nome>(<args>) set search_path = public, pg_temp;
```
- **O cliente logado chama via `supa.rpc()`** (ex. `cache_omdb_rating()`, `cache_tmdb_info()`) — revoga de todo mundo do mesmo jeito, mas concede de volta só pra `authenticated` (nunca `anon`, que nunca tem sessão real; o app inteiro exige login pra fazer qualquer coisa):
```sql
revoke execute on function public.<nome>(<args>) from public, anon, authenticated;
grant execute on function public.<nome>(<args>) to authenticated;
alter function public.<nome>(<args>) set search_path = public, pg_temp;
```
Nesse segundo caso a barreira de escopo não é "quem pode chamar" (é o próprio cliente logado, de propósito) — é o que o corpo da função tem permissão de fazer: `cache_tmdb_info()`, por exemplo, só escreve `tmdb_cache`/`tmdb_atualizado_em` do filme recebido, nunca lê nem escreve mais nada.

(`search_path` fixo pelo mesmo motivo nos dois casos — nasce junto, não é corrigido depois num scan de advisories.)

**Sem essa distinção escrita, o risco é real**: alguém lendo só a regra geral (revogar de `authenticated` também) pode "consertar" o grant de `cache_omdb_rating`/`cache_tmdb_info()` achando que está fechando uma brecha, e quebrar a escrita de cache pro app inteiro — motivo de registrar isso agora (2026-08-24), depois de a distinção ficar implícita por tempo demais.

Aplicado ao primeiro caso em `recalcular_compatibilidade()` e à sua wrapper de gatilho `_trg_recalcular_compatibilidade()`: ambas `SECURITY DEFINER`, `search_path` fixo, `EXECUTE` revogado de `public`/`anon`/`authenticated` (só `postgres`/`service_role`) — confirmado por leitura direta de `pg_proc`. `get_advisors(type='security')` rodado depois de criar os gatilhos de conquistas e compatibilidade: nada além do `auth_leaked_password_protection` já conhecido (ver Pendência abaixo). Aplicado ao segundo caso em `cache_omdb_rating()` e `cache_tmdb_info()`: `EXECUTE` confirmado (leitura de `information_schema.routine_privileges` + `has_function_privilege('anon', ..., 'EXECUTE')` retornando `false`) só pra `postgres`/`service_role`/`authenticated` — sem `anon`, sem `public` solto. `get_advisors(type='security')` depois da migração de `cache_tmdb_info()` (2026-08-24) só sinaliza o padrão esperado (`authenticated_security_definer_function_executable`, mesmo aviso que `cache_omdb_rating()` já carregava, intencional pros dois) mais o `auth_leaked_password_protection` já conhecido — nada novo.

Views (`v_avaliacao_comparativo`, `v_filme_stats`) usam `security_invoker=true` — sem isso, uma view roda com o privilégio de quem criou, não de quem consulta, o padrão antigo do Postgres pra views sem essa opção declarada. Seguro porque `avaliacoes`/`filmes` já abrem `SELECT` pra `public`; `usuarios` abre só pra `authenticated`, o mesmo papel que qualquer sessão logada real já usa. Validado com sessão `authenticated` real no app (celular, logado) depois da migração — Estatísticas, Afinidades e Conquistas, as três telas que dependem dessas views, carregaram normalmente.

**Regra irmã, mesmo padrão**: toda policy de escrita nasce com o escopo mais largo possível se ninguém restringir — igual ao `EXECUTE` de uma `SECURITY DEFINER` acima. `perfis.perfil_write` era `FOR ALL TO public`: a escrita só era barrada pela condição (`auth.uid()` é sempre `NULL` pra quem só tem a anon key, sem sessão), nunca pelo escopo de role. **Escopo por comando (`FOR INSERT`/`UPDATE`/`DELETE`, nunca `ALL` por hábito) e por role (`TO authenticated`, nunca `public` por padrão) é parte de criar a policy, não um passo separado pra lembrar depois** — se a condição um dia mudar ou tiver um bug, o role é a segunda barreira que sobra. Este é o terceiro caso do mesmo padrão de escopo-largo-demais nesta leva (função `SECURITY DEFINER` exposta via RPC, `compatibilidade` sem RLS nenhuma, e agora esta policy `TO public`) — é o que justifica a regra existir, não coincidência.

**Pendência separada, fora de qualquer migração**: `auth_leaked_password_protection` está desabilitado no Supabase Auth (não checa senhas comprometidas via HaveIBeenPwned). É configuração de Auth, não schema — decidir e aplicar quando fizer sentido, sem misturar com migração SQL.

### Auth & admin

Login is Supabase Auth email/password (`supa.auth.signInWithPassword`/`signUp`/`resetPasswordForEmail`). After a successful auth, `onLogin()` does a live `usuarios` lookup by email — if it comes back empty the account exists but isn't a recognized member yet (shown as a distinct message, app doesn't load). There's no roles table; admin access is a single hardcoded email check (`ADMIN_EMAIL`) gating the admin panel UI and its Supabase writes (which are enforced by RLS server-side too, not just hidden client-side).

### Notifications

Push (FCM) is wired through a separate Google Apps Script deployment that the app calls via a plain `fetch` to a Web App URL (`APPS_SCRIPT_URL` in `index.html`), since a static GitHub Pages site can't send push itself.

**The real code lives only in Apps Script, never in this repo.** Project "API Filmes", file `apps_script_fcm.js.gs` (the same Apps Script project also has `CineList_API_FlutterFlow.gs`, leftover from an earlier version of the app — unused, don't touch). `apps_script_fcm.js.gs` holds the Firebase private key and the Supabase `service_role` key in plain text; this repo is public (GitHub Pages), so neither key can ever be committed here. There is no `.js` copy in this repo — see "Why no copy" below for why that's deliberate, not an oversight.

What the script does: `doGet(e)` routes on the query string — `?acao=criarUsuario` calls `criarUsuarioHandler()` (creates a member row in `usuarios` via the Supabase Admin API, backs the admin panel's "criar membro" flow), anything else sends a push via `sendPush()`. `doPost()` is a Supabase webhook handler with dedup logic — **confirmed dead** (2026-09-01): no trigger in the database points at it, nothing calls it. Editing the script and saving is not enough to deploy it — changes only go live by editing the **existing** implantação (Implantar → Gerenciar implantações → ✏️ editar a implantação já publicada → Versão: Nova versão → Implantar), **never** by creating a new implantação. A new implantação gets its own URL, different from the one already hardcoded as `APPS_SCRIPT_URL` in `index.html` — creating one instead of editing the existing one silently leaves the live app calling the old, unedited deployment. Confirmed the hard way (2026-09-01): the first attempt at the fix below used "Nova implantação" — following an instruction that turned out to be wrong, inherited from this same script's own now-deleted repo copy (its header comment used to say the opposite: "Cada vez que editar, publique uma NOVA implantação... senão as mudanças não refletem") — and had to be redone against the existing implantação instead.

**Current `sendPush()`/`doGet()` contract** (applied by hand in the Apps Script editor on 2026-09-01, fixing the "filme adicionado" notification duplicating and always opening the home instead of the film): `sendPush(accessToken, token, title, body, url)` sends only a `data` payload (`title`, `body`, `url` — all strings) — no `notification` key at the message's top level, and no `webpush.notification`/`webpush.fcm_options.link` either. Both are "notification"-typed fields that make the FCM SDK auto-display the push on top of `sw.js`'s own manual `onBackgroundMessage` display — that double display was the duplicate. Icon/badge/vibrate aren't lost: `sw.js`'s `onBackgroundMessage` already sets them by hand (`icon`/`badge`: `./icon-192.png`, `vibrate: [200,100,200]`) as part of that manual display. `doGet(e)` reads a new `e.parameter.url` and passes it through to `sendPush()` as the 5th arg; `index.html`'s `enviarNotifFilme()` is the only caller that populates it today (the film's `#/filme/<id>` URL) — the other three push call sites (aniversário, notificação manual do admin, teste de diagnóstico) still call the Apps Script URL without a `url` param, so they fall through to `sendPush()`'s default (`https://lbatinga.github.io/cinelist/`), same as before.

**Why no copy of the script lives in this repo**: a file that never executes but looks like real code is a trap — it goes stale silently (nobody remembers to hand-sync it on every Apps Script edit) and invites being pasted back over the real deployment by someone who assumes it's current. That's not hypothetical: on 2026-09-01, this repo's `apps_script_notificacoes.js` had drifted from the deployed script (wrong response helper name, wrong token-list shape, an `isTest` param that doesn't exist for real, no `criarUsuarioHandler`/`doPost`/`USER_NAMES` at all) and came within one paste of overwriting the live script, which would have deleted `criarUsuarioHandler` — the function the admin panel's "criar membro" flow depends on. The file was deleted rather than corrected, because a corrected copy has the exact same staleness risk the moment the real script changes again without this repo being told. If you need to change the push notification logic, edit it directly in the Apps Script editor (script.google.com, project "API Filmes") and deploy a new implantação — there is nothing to sync back here afterward.

### Compartilhamento (WhatsApp) e Open Graph

**O botão "WhatsApp" do painel de filme foi removido em 2026-09-01** — sem uso real que justificasse manter (motivo que também descartou o item 2 da lista de pendências, contagem de uso de botões). Junto saiu todo o código que existia só pra ele dentro de `filmDetailHTML()`: a montagem do texto (`wpp`), a nota formatada (`notaWpp`, que por sua vez era o único uso de `avCount`) e a URL do filme (`filmeUrl`, `location.origin + location.pathname + '#/filme/' + f.id`) — nenhuma dessas variáveis tinha outro consumidor no arquivo. O link de filme em si (`#/filme/<id>`) continua existindo pra outros usos (roteamento, deep link) — só a montagem específica pro texto do WhatsApp foi embora.

**As meta tags Open Graph no `<head>` continuam — não dependiam do botão.** Elas servem qualquer link do app compartilhado em qualquer lugar (WhatsApp, Telegram, Slack, o que for), não só pelo botão que saiu — copiar e colar a URL do app em qualquer chat já aciona o crawler que lê essas tags. São genéricas de propósito, não por filme, e isso não é "fazer depois", é limitação de arquitetura. O crawler que gera a prévia de link do WhatsApp lê só o HTML estático que o servidor devolve, sem executar JavaScript e sem nunca ver o hash da URL (`#/filme/<id>` não é enviado ao servidor em requisição nenhuma — é só um fragmento interpretado no navegador). Ou seja: não importa qual filme a pessoa está compartilhando, o crawler sempre recebe o mesmo `index.html`, com as mesmas `<meta property="og:...">` fixas. Pra ter pôster/nota por filme na prévia seria preciso ou (a) uma página HTML real por filme com suas próprias meta tags — 862 arquivos hoje, regerados a cada filme adicionado — ou (b) renderização no servidor decidindo as meta tags por request; nenhuma das duas cabe no GitHub Pages, que só serve arquivos estáticos. Enquanto o app morar ali, a prévia é sempre a mesma: logo (`icon-512.png`) + nome + descrição curta do app.

Texto por regra calculada, não molde único (sete linhas iguais viravam tabela) — a primeira regra que casar ganha: chegou ao 1º ("assumiu a liderança"); chegou ao 2º/3º ("subiu ao pódio"); passou 2+ pessoas de uma vez ("saltou de Xº para Yº"); recuperou uma posição que já teve antes no período calculado ("retomou o Xº de {quem}" — confirmado disparando nos dois sentidos numa disputa real de ida e volta entre duas pessoas); caso simples ("passou {quem} e chegou ao Xº"). Cada item tem um disco CSS puro com o número da posição alcançada (ouro/prata/bronze pro pódio, neutro do 4º em diante) — nunca emoji de medalha. No celular, sem gráfico nem seletor de período: usa o histórico completo mês a mês (sem os blocos do "Tudo" do desktop, que só existem pela densidade visual do gráfico) em vez de ficar presa num período sem controle pra mudar.
    - **Gráfico de posições** — só desktop, omitido (não encolhido) no celular: 15 linhas não cabem legíveis em tela estreita. Uma linha por pessoa, posição no eixo vertical, meses no horizontal, nome no fim da linha. Todo membro do ranking entra, não só um top fixo. Seletor de período 6/12/18 meses/Tudo, **padrão 6** (não 12 — ajustado depois do teste ao vivo); os três recortes fixos são sempre mensais, "Tudo" comprime o histórico inteiro em no máximo 18 pontos (mesmo teto do maior recorte mensal) — tamanho de bloco calculado, contado a partir do fim, pro mês atual sempre aparecer. É amostragem, não soma: cada ponto é a posição no último mês do bloco, viradas dentro do bloco somem — aviso na tela informa o tamanho do bloco em uso.

    **Cor por pessoa — duas tentativas descartadas antes da que ficou**, todas via teste ao vivo com os 15 do ranking real, não achadas por inspeção de código: (1) `getProfile(uid).color || aC(uid)`, a fonte que `avatarHTML()` já usa — rejeitada porque `aC()` só tem 9 cores fixas pra até 16 pessoas (colisão exata acima de 9) escolhidas pela ordem de cadastro no Supabase, sem nenhuma relação com quem fica vizinho no gráfico. (2) Matiz calculado por índice (`360°/total`), com e sem luminosidade alternada por paridade — ainda insuficiente: a faixa de verdes comprime muito perceptualmente, dois verdes a 24° de distância um do outro ainda pareciam quase iguais na tela real. Ficou: paleta categórica fixa (Tableau10 + suas 10 variantes claras), atribuída pelo índice na lista já ordenada por posição atual — os 10 primeiros (a maioria da tropa hoje) caem em matizes totalmente diferentes entre si por construção, não por sorte. `getProfile(uid).color` **nunca** é usado aqui, nem como prioridade sobre a paleta: `avatar_color` é sorteado na criação do usuário, não escolhido por ninguém, e um sorteio coincidindo com o vizinho calculado (achado ao vivo: Batinga laranja vs Jheffeson laranja da paleta, Raissa verde vs Thales verde-claro da paleta) já bastou pra recriar o mesmo problema que a paleta existe pra resolver. O avatar do app continua usando `getProfile`/`aC()` normalmente — só o histórico (linhas do gráfico e nomes coloridos na lista de viradas) usa a paleta nova.

    **Aviso obrigatório na tela** (não é opcional, é o que torna o gráfico honesto): as avaliações sem data contam no total mas aparecem como se estivessem lá desde o início, então posições de 2025 podem estar adiantadas pra quem tem muitas sem data.

## Working conventions established in this repo

- Commits are small and scoped to one logical change each; stage `index.html` (and only the specific other files actually touched) explicitly rather than `git add -A`, since untracked scratch/export files (`*.csv`, `backups/`) are gitignored but other stray local files may not be.
- Never commit CSV files or anything under `backups/` — both are gitignored on purpose (DB exports/backups are local-only, not repo content). Don't override the ignore for a one-off "just this once".
- Show the diff and wait for explicit approval before committing or pushing.
- **"Show the diff" means paste the literal diff text inline in the chat message, in a code block — for any file (CLAUDE.md, index.html, SQL migrations).** Never say "shown above," never rely on a tool-rendered diff view or file panel — it does not reach the user in this setup, and every time it happens it burns a full round-trip just to get it re-pasted as text.
- **The cycle is four separate steps, in order: diff pasted inline → user approves → commit → push.** Pasting the diff and committing in the same turn is not "showing the diff," even when the diff is small (a one-line fix) or obviously correct — commit only after the user's own message approves it, not right after your own message that includes the diff. Push is its own separate ask on top of that, same as before.

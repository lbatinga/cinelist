# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CineList is a collaborative movie-tracking PWA for a closed group of friends (Netflix-style catalog, ratings, stats, ranking). It is a **single-file vanilla JS/CSS/HTML app with no build step, no package manager, and no test suite** — `index.html` (~330KB) contains the entire app: all CSS in one `<style>` block and all JS in one `<script>` block. There is no `package.json`.

Backend is Supabase (Postgres + Auth), project ref `iznikddtdwfvkkwqtwxg` (i.e. `https://iznikddtdwfvkkwqtwxg.supabase.co`, matching `SUPA_URL2` in `index.html`). Hosting is GitHub Pages, deployed by pushing to `main` (auto-publishes; Fastly CDN in front has a ~10 min edge cache, so a just-pushed change may take a few minutes to show up live — verify with a cache-busted `curl` if it matters, not by re-pushing).

## Commands

There is no build/lint/test tooling — edit `index.html` directly.

- **Run locally**: serve the directory with any static file server, e.g. `python -m http.server 8080`, then open `http://localhost:8080`. The Service Worker and push notifications require HTTPS, so those specific features won't work over plain `http://localhost`.
- **Deploy**: `git push` to `main` — GitHub Pages serves directly from the repo root, no CI/build step.
- **Verify a change without a browser**: tables with an open `SELECT` policy (`filmes`, `avaliacoes`, `perfis`, `conquistas`, `compatibilidade`) can be queried directly via the REST API using the anon key already embedded in `index.html` (`SUPA_URL2`/`SUPA_KEY2`), e.g. `curl "$SUPA_URL2/rest/v1/filmes?select=id&limit=1" -H "apikey: $SUPA_KEY2"`. Useful for checking row counts or schema without waiting on the UI. `usuarios` requires an authenticated session (anon key alone returns nothing) and `fcm_tokens` has no public read policy either — both expected, not a bug.
- **DB export/backup**: `scripts/backup-console.js` is meant to be pasted into the browser DevTools console on the live, logged-in app (see `scripts/README.md`) — it reuses the page's already-authenticated Supabase client (`supa`) to dump all four tables to CSV, which sidesteps the `usuarios` RLS restriction. There is no Node-based equivalent in this environment/repo (no Node install was available when this was built; do not assume one exists).

## Architecture

### Data flow: `STATIC` seed → live Supabase overwrite

`index.html` embeds a `const STATIC = {...}` JSON blob (near the top of the main `<script>`) that seeds the initial in-memory state (`RAW.usuarios`, `RAW.users_stats`, etc.) before the network round-trip to Supabase completes. Historically this blob held full frozen snapshots of every derived stat, which caused real bugs (a stale "não quero assistir" list kept getting merged back in after being deleted from the DB; a login gate that trusted the frozen member list instead of a live query). Most of `STATIC`'s keys have since been emptied out — only `STATIC.usuarios` still carries real seed data, because `applyUserToUI()`/`buildUD()` synchronously read `USERS` (aliased to `RAW.usuarios`) during the very first paint after login, **before** the background fetch (`loadFilmsFromSupabase()` → `loadUsuariosFromSupabase()` → `calcUserStats()`) has resolved. Every other `RAW.*` key derived from `STATIC` (stats, highlights, monthly activity, per-user personal stats, available years/genres, recent-films list) is fully recomputed from live `FILMES`/`STATS` inside `calcUserStats()` on every load, so their `STATIC` seed values are inert placeholders (kept as `{}`/`[]` rather than removed, since other code reads `RAW.xxx` unconditionally).

If you ever need to hand-edit the `STATIC` line: it's one extremely long line (tens of KB), so `Read` with a line range will blow the tool's token cap — extract/patch it with `awk`/`sed`/PowerShell's `ConvertFrom-Json`/`ConvertTo-Json` instead of trying to view it directly. The file is UTF-8 without BOM, CRLF line endings — preserve both if you touch it outside the normal `Edit` tool.

### Global state (top of the main `<script>`)

- `RAW` — the mutable root object; most other globals are references into it.
- `USERS` = `RAW.usuarios` (keyed by `legacy_id`, e.g. `"USER-003"`), `STATS` = `RAW.users_stats` — both cleared and rebuilt wholesale by `loadUsuariosFromSupabase()` on every load (`Object.keys(...).forEach(delete)` then `Object.assign`), not merged.
- `FILMES` (array) / `FILMES_MAP` aliased as `FM` (object by id) — the catalog, populated by `loadFilmsFromSupabase()`.
- `CU` — the logged-in user's `legacy_id` (their "current user" key into `USERS`/`STATS`).
- `profileData` — keyed by `legacy_id`, sourced from the `perfis` table (apelido, bio, avatar, birthday, favorite film id) via `getProfile(uid)`.
- `supa` — the Supabase client (`window.supa`), created once at the top with the anon key; carries the authenticated session after login.

### Rendering

No framework — every view is a function that builds an HTML string and assigns it to `.innerHTML`. `render()` is the dispatcher that re-renders whichever top-level view (`CV`) is currently active (`renderHome`/`renderFilmes`/`renderPendentes`/`renderAvaliacoes`/`renderRecentes`/`renderRanking`/`renderDescobertas`). Film detail panels are duplicated per view (`#filmDetailPanel`, `#pendDetailPanel`, `#avDetailPanel`, `#recentDetailPanel`, plus a mobile full-screen modal `#mfmContent`) and each write action (rate, mark "não quero", add film) has to explicitly re-render whichever of these panels is currently showing the affected film — `render()` alone does not do this, since it may re-render a detail panel to a different film entirely. `displayName(uid)` and `avatarHTML(uid, opts)` are the shared helpers for showing a member's name/avatar with `perfis` apelido/photo fallback to `usuarios.nome`/generated color+initials — use these instead of reading `USERS[uid].nome` directly when adding a new place that shows a member.

Esc handler: a single global listener closes whatever overlay is open deepest-first (reused across every modal — the trilha modal was first to need it). A new overlay just adds a line to that one list; don't write a per-modal Esc listener.

**A view's sub-state must survive an unrelated `render()` call, or on-demand data loading will silently undo user navigation.** Any function that lazy-loads data (e.g. `loadComparativoParaUsuario()`) calls the generic `render()` on success to refresh whatever's on screen — but `render()` only knows about the top-level `CV`, not what's drilled into inside that view. Descobertas already got this right: `renderDescobertas()` re-reads `window.perfilSelecionadoUid` every time, so a stray `render()` just repaints the same profile. Ranking didn't, until a real bug proved it: clicking a member in the Ranking tab opened their profile, `userDetailHTML()` kicked off `loadComparativoParaUsuario(uid)` in the background (undefined comparativo cache), and when that fetch resolved — often within the same click-to-click window — its `render()` call ran `renderRanking()`, which rebuilt `#rankTabContent` back to the plain tab list with no memory that a profile had been opened. First click looked like it opened and instantly closed; the second click "worked" only because that uid's comparativo was cached by then, so no fetch and no clobbering `render()` fired. Fixed by giving Ranking the same pattern Descobertas already had: `rankDetailUid` (module-level) holds which profile is open in `#rankTabContent`, `renderRankTab()` checks it before falling back to the tab list, and both entry points that should exit the profile (`closeRankDetail()`, `setRankTab()`) explicitly clear it. **Known follow-up, not fixed**: the year-drilldown reachable from inside a profile (`openUserYearDetail`, clicking a year bar on someone's page) is a second layer of sub-state nested inside the first — if `loadComparativoParaUsuario`'s `render()` fires while that year view is open, `renderRankTab()` still redraws the *profile* underneath it (since `rankDetailUid` is untouched by entering the year view), clobbering the year view the same way the original bug clobbered the profile. Any future screen that adds on-demand data loading needs to ask this same question up front: does its sub-state survive a `render()` call it doesn't control?

### Dates

Always build "today" as a local calendar date with `localDateStr(d)`, never `new Date().toISOString().split('T')[0]` — `toISOString()` is UTC and rolls over to the next day in the evening in Brazil (UTC-3), which previously caused `avaliacoes.data_avaliacao` to be off by one day. `toISOString()`/`Date.now()`-style values are still correct for genuine instants (`created_at`/`updated_at` timestamp columns, backup export filenames) — the distinction is calendar-date-as-seen-by-a-human vs. absolute-instant.

| `usuarios` | `legacy_id` (text PK, e.g. `USER-003`) | Membership list. SELECT requires an authenticated session (anon key alone returns nothing). `in_ranking` (bool) controls ranking inclusion, and triggers two downstream recalcs — see Conquistas and Compatibilidade. A DB trigger auto-generates the next sequential `legacy_id` (`USER-NNN`) when a new row is inserted with that field left empty — the admin "criar membro" flow relies on this and only sends `legacy_id` explicitly when overriding it. | `compatibilidade` | `(a, b)` composite, `a < b` always | State, not history — one row per pair of `in_ranking=true` usuários, fully overwritten on every recalc. ### Conquistas (achievement trilhas)

`conquistas` records, once and permanently, the moment each member crosses each tier of an achievement trilha (Volume, Curadoria, Pioneirismo, Maratona Mensal, Tempo na Tela, Diversidade de Gêneros, Viajante do Tempo, Filmes Longos, Consistência, Influência). It's populated by replaying `avaliacoes`/`filmes` per user — not something `index.html` computes; there is no client-side "conquistas" calculation.

**Trilha vs. especial — not the same nature, and it's easy to trip on this**: a **trilha** is história — frozen, never revoked, has a date, lives in `conquistas`. A **especial** is *estado* — recalculated live from current data every render, can be lost if the underlying condition stops holding (e.g. the tropa's average for a film shifts and a Defensor case no longer qualifies), and has no achievement date because there isn't one to have. Especiais are never written to `conquistas` — same nature as `compatibilidade`, which is also *estado*. **The UI must never notify or show a delta when a especial is gained or lost** — same rule as compatibilidade, opposite of a trilha tier.

**Especiais set (current, 7): Otimista, Crítico, Fã de \<gênero favorito da pessoa\>, Apaixonado, Defensor, Estraga-Prazeres, Termômetro.** Computed live off the Fase 3 views (Defensor/Estraga-Prazeres/Termômetro — see Base de comparação) or off `RAW.users_stats`/`FILMES` directly (the other four), same pattern as compatibilidade. "Fã de \<gênero\>" is dynamic per person (40%+ of their filmes in their own `fav_genre`) — not hardcoded to one genre. **Apaixonado** (3+ notas 10) is what survives of an older multi-tier "Notas 10" ladder: the tiers past the first rewarded rating inflation (someone who rates with real judgment never gets there), but "gave a 10 at least a few times" is a real trait, so only the binary first tier survives. **Retired, do not reintroduce**: Bom Humor (duplicated Otimista's axis), Difícil de Agradar (duplicated Crítico's axis), Implacável (required five notas 0, which nobody in the tropa has — a especial that zeros isn't a especial, same calibration rule as below). Voz Dissonante stays cut — see Base de comparação for why and the revisit idea.

**Selo nunca revogado**: once a `(usuario_id, trilha, tier)` row exists, no normal run ever updates or deletes it — every insert (backfill or incremental) uses `on conflict (usuario_id, trilha, tier) do nothing`. This holds even when the underlying condition later stops being true — Pioneirismo can lose its condition the moment someone else rates a "solo" film, and **a duplicate-film merge can retroactively lower any counter** — but the achievement date/precision already on record must never change.

**Correction model**: because of the above, deleting rows and re-running is only safe while a `versao_backfill` tag is still a genuine test tag (see below). Once a tag is promoted, fixing bad data is an incremental replay — the same insert, same `on conflict do nothing` — never `delete` + re-run, since a delete would let the next run silently mint a *different* date for an achievement someone already experienced.

**`versao_backfill`** means *origin of the row*, not "which backfill execution" — the two values in use are permanent, not test tags to eventually clean up. `v1` = the one-time historical backfill (196 rows). `gatilho` = every row inserted automatically, forever, by the triggers below — the same tag on every firing, not a per-execution id. **Do not delete `gatilho` rows as if they were leftover test data** — they're real achievements dated the day the trigger caught them. The "wipe while under test" pattern (`delete from conquistas where versao_backfill = '<tag>'`) only applies to genuine one-off test tags (e.g. `'incremental-teste'`) — never to `v1` or `gatilho`.

**Replay incremental**: `recalcular_conquistas(p_versao_backfill text default 'incremental')` is a `SECURITY DEFINER` SQL function (needed since `conquistas` has no insert policy for anon/authenticated) that recomputes all 10 trilhas' live values for every usuário and inserts any newly-crossed tier with `data=current_date`, `precisao='exata'` — an incremental crossing is always dated in real time; `indeterminada` only ever applies to the frozen historical batch, never to anything the trigger inserts. Two triggers call it, both `FOR EACH STATEMENT` (fires once per command, not once per row — a future bulk import in one multi-row `INSERT` only recomputes once; if a bulk job ever needs many separate single-row statements instead, disable the trigger for that operation with `alter table <tabela> disable trigger <nome>` and re-enable after):
- `avaliacoes_recalcula_conquistas` (AFTER INSERT OR UPDATE on `avaliacoes`)
- `filmes_recalcula_conquistas` (AFTER INSERT on `filmes`) — needed separately because adding a filme without rating it is a real, common flow (the add-film UI defers rating with an "avalie agora 👇" prompt, per `index.html:2292`), and Curadoria's counter depends only on the insert, never on an avaliação.

Full recompute (every usuário, not scoped to just the writer) is deliberate: Influência credits the *inserter* of a filme when *someone else's* rating pushes it past the approval threshold, so a trigger scoped to "recompute only whoever just wrote" would never light up Influência for anyone. The one trilha where writer-scoping would work (Pioneirismo) is harmless the other way too — a third party's rating can only ever lower someone else's *live* Pioneirismo count, never cross them a new tier, and a dropped live value never revokes a recorded selo. Measured cost of a full recompute across every usuário: **~53ms**, paid once by whichever transaction triggered it.

**`precisao='indeterminada'`** (with `data=null`) marks a tier crossed while replaying the ~1,293-row undated migration batch in `avaliacoes` (see the schema table above). Only Volume, Tempo na Tela, Diversidade, Viajante do Tempo and Filmes Longos can land there. **The indeterminada case must never say "antes de 2025" or guess a year** — dated `avaliacoes` rows go back to 2023, and the undated rows just lost their registro, not necessarily old. Maratona Mensal and Consistência already exclude undated rows from their own counters entirely (an older, unrelated decision — see the "avaliações sem data" warnings surfaced in the Conquistas/Ranking UI); Curadoria always has a `created_at` fallback so it's never indeterminate; Pioneirismo and Influência depend on *other* members' dated activity so they essentially never land in the undated block either.

**Degraus infinitos (trilhas sem teto)**: Volume, Curadoria, Pioneirismo, Maratona Mensal, Tempo na Tela, Filmes Longos, Consistência and Influência have no ceiling — past the last named tier, more are generated up to 12 total per trilha (named + synthetic) using

```
passo   = max(5, 5 * 10^(dígitos(limiar) - 2))
próximo = ceil(limiar * 1.3 / passo) * passo
```

(`dígitos(x)` = number of digits in `floor(x)` — this proportional step, not a flat `/25`, is what keeps the ladder sane at both small scale, e.g. Consistência's 24→35→50→65→85, and large, e.g. Volume's 900→1200→2000→3000). The synthetic tier's name is the last named tier's selo plus a roman numeral (`Divindade II`, `Divindade III`, ...), except Tempo na Tela, whose synthetic name is just the value with a pt-BR thousand separator (`1.500 Horas`). Diversidade de Gêneros and Viajante do Tempo are capped ("teto") trilhas and never get synthetic tiers.

**Catálogo canônico de degraus** — this table is the single source of truth for every named tier. `index.html` must define this catalog in exactly one place (a single array/object), consumed both by the live "current value + progress to next tier" calculation and by any future replay/backfill tooling — two lists is what caused an earlier drift between the client-side ladder and the DB backfill.

### Base de comparação com a tropa

Two views feed both the compatibility formula and the leave-one-out especiais below. Both are plain (non-materialized) views — the dataset is small enough (841 filmes, `in_ranking` usuários) to recompute live, so no refresh strategy is needed. Both scope to `nota is not null` and `usuarios.in_ranking = true`; dated and undated `avaliacoes` rows are both included (excluding undated rows would drop 38% of the base — see the `avaliacoes` schema row above). Both use `security_invoker=true` — see Segurança below.

- **`v_filme_stats`** — per-filme `n_avaliacoes`, `media_tropa` (full population), `variancia` (`var_pop`, not `var_samp` — `var_samp` doubles the variance at n=2, which would inflate exactly the small samples that should carry the least weight), `peso` (`variancia / média_da_variância_dos_filmes_com_n≥2`, clamped to `[0.25, 2.2]`). Filmes with `n_avaliacoes = 1` are excluded entirely — a film only one person rated can never be a "filme em comum" between two people, so including it only pollutes the peso distribution (it would always sit at the floor).
- **`v_avaliacao_comparativo`** — one row per avaliação, with three distinctly-named means so they never get swapped: `media_pessoa`/`desvio_pessoal` (that person's own average across their own avaliações — feeds the Pearson correlation in Compatibilidade), `media_tropa`/`desvio_tropa` (the full-population average from `v_filme_stats` — feeds peso/compatibilidade, never leave-one-out), and `media_tropa_sem_ele`/`desvio_tropa_sem_ele`/`n_outros` (leave-one-out, excludes the person's own nota — feeds only the especiais below, never compatibilidade).

**Regra de método**: leave-one-out vale para todo selo/especial que compara uma pessoa contra a tropa — sem isso a pessoa competiria contra a própria contribuição (com n=4, uma nota isolada já é 25% da média). NÃO vale para peso/compatibilidade — ali a variância é propriedade do filme, não de quem está sendo comparado.

**Regra de calibração** (vale pra estes especiais e pra qualquer especial futuro): alvo de 1 a 4 pessoas por especial num grupo pequeno (calibrado com 14 `in_ranking` — o que importa é ficar raro, não o número exato). Especial que zera não existe; especial que 11 de 14 têm não é conquista, é comportamento normal da base.

**Especiais calibrados sob essa regra** (todos leave-one-out, `n_outros ≥ 4`, i.e. 5 avaliações no total — a mediana de avaliações por filme na base é 4, então esse piso é o "normal" da base, não um corte artificialmente apertado):
- **Defensor** — `media_tropa_sem_ele < 6.5` e `nota ≥ 8`.
- **Estraga-Prazeres** — `media_tropa_sem_ele > 8.2` e `nota ≤ 6`. `nota ≤ 6` foi calibrado, não escolhido: com `≤ 5` (o corte simétrico "óbvio" ao 8+ do Defensor) dava 1 caso em 1 pessoa — a tropa avalia alto demais para "dar 5 num filme amado" acontecer.
- **Termômetro** — 60%+ das avaliações elegíveis a menos de 0,5 de `media_tropa_sem_ele`, piso de 50 filmes elegíveis (`n_outros ≥ 4`). 60% também foi calibrado: com tolerância de 0,5 mas sem corte proporcional (contagem absoluta), 11 de 14 pessoas ganhavam — o selo saturava, porque a tropa concorda demais para "estar perto da média" ser incomum.

6.5 ("tropa afundou") e 8.2 ("tropa amou") são estatisticamente simétricos — mesma fração de filmes (11,5%) de cada lado da distribuição de `media_tropa` — não valores redondos escolhidos à mão.

**Voz Dissonante — cortado, não faz parte do set atual.** O critério original (10 filmes a 3+ pontos da média) dá zero pessoas: a tropa concorda demais para "discordar muito" acontecer 10 vezes com distância bruta. Um corte proporcional (15%+ das avaliações a 2+ pontos, piso de 50) também zera; forçar pra baixo (5%) só captura "discordar de 1 filme em 20", que numa tropa homogênea é ruído, não característica de personalidade. **Ideia a revisitar**: usar o `peso` de variância de `v_filme_stats` — discordar especificamente nos filmes que racharam a tropa (peso alto), não distância bruta da média num grupo que raramente racha.

### Compatibilidade

Compatibility score between pairs of `in_ranking=true` usuários, stored in `compatibilidade` as *estado* — fully overwritten on every recalc, no history, same nature as especiais and for the same reason: it can legitimately go up or down as anyone rates anything, and the UI must never show a delta or notify on change.

**Fórmula (v2, tag `versao_formula = 'v2'`)**: weighted Pearson correlation over `desvio_pessoal` (from `v_avaliacao_comparativo`) on filmes em comum between a pair, weighted by `peso` (from `v_filme_stats` — peso is a property of the filme, not of who's being compared). `r_bruto = Σ(peso·da·db) / √(Σ(peso·da²)·Σ(peso·db²))`, clamped to `[-1, 1]` to absorb float rounding at the edges (matters mainly at `n_comum=1`, where the raw ratio is always exactly ±1 by construction and can briefly round past it). Sample-size brake: `r_ajustado = (n/(n+K))·r_bruto + (K/(n+K))·r_grupo`, `K=15`, `r_grupo` = average `r_bruto` across all pairs with data in that run (stored per-row in `media_grupo` for audit, even though it's the same value for every pair in a given run). Display: `pct = round(50 + 50·r_ajustado)`.

This replaced an older client-side formula (raw shared-film note-difference, minimum 3 filmes em comum) that was imprecise at the top of its range and treated raw note distance as agreement even when two people were just equally generous — exactly what `desvio_pessoal` fixes. `K=15` was validated against the brake's actual behavior — a genuinely high `r_bruto` from a small sample still lands near its raw value (e.g. `n_comum=1` around pct 72, not shoved to the group average); the brake stops small samples from *outranking* large well-supported ones, not from mattering at all — and isn't being recalibrated without new evidence. A faixa de `pct` de qualquer execução é retrato daquele momento, não propriedade da fórmula — ela muda sozinha quando entra ou sai membro, então um mínimo mais baixo numa sessão futura não é regressão.

`recalcular_compatibilidade(p_versao_formula text)` upserts every `in_ranking` pair by `(a,b)`, recomputing membership (`select legacy_id from usuarios where in_ranking = true`) from scratch on every call — so it always produces the full current cartesian product, not just pairs already in the table. **Pairs with zero filmes em comum get `n_comum=0` and `pct = NULL`**, never collapsed to `r_grupo` — a number with no basis is worse than no number; the UI reads `pct is null` as "ainda não dá pra comparar."

**`n_comum >= 15` é o limiar de confiabilidade** (distinto de `pct = NULL`, que é limiar de existência — zero filmes em comum). O corte reusa o próprio `K=15` da fórmula, não é um número novo: o peso do sinal real em `r_ajustado` é `n/(n+K)`, que só ultrapassa 50% quando `n >= K` — abaixo disso, mais da metade do número é a média do grupo, não o gosto da pessoa. Pares abaixo do limiar são *estado próprio* na UI (ex. "ainda conhecendo o gosto de {Nome}" — número presente mas apagado, sem cor de faixa, ordenado por último), nunca escondidos ou tratados como afinidade baixa de verdade.

**Disparo do recálculo: gatilho em `usuarios` + `pg_cron` diário, não só manual.** Dois problemas de natureza diferente motivam os dois mecanismos. Um membro novo (`in_ranking` passa a `true`) fica sem nenhuma linha em `compatibilidade` até alguém rodar a função de novo — isso é *existência*, resolvido por dois gatilhos `AFTER INSERT/UPDATE FOR EACH ROW` em `usuarios` (`usuarios_entra_ranking_recalcula_compat`, `usuarios_promovido_ranking_recalcula_compat`, condicionados a `in_ranking=true`) chamando a função wrapper `_trg_recalcular_compatibilidade()`. Isso não cobre a *deriva* de alguém que já existe e segue avaliando — o gatilho só dispara em mudança de `in_ranking`, não em cada avaliação nova. Por isso também um `pg_cron` diário (`recalcula_compatibilidade_diario`, 07:00 UTC = 04:00 Brasília — `cron.timezone` do projeto é GMT, e o Brasil não tem horário de verão desde 2019, sem variação sazonal a corrigir) rodando `recalcular_compatibilidade('v2')`. Rejeitado: disparo no carregamento do app por idade do `calculado_em` — exigiria abrir `EXECUTE` da função pra `authenticated`, contra ganho quase nulo num grupo de ~15 pessoas com recálculo de ~132ms.

**Nota sobre pg_cron especificamente, pra não confundir uma sessão futura**: a extensão foi vetada explicitamente numa fase anterior, quando a fórmula de compatibilidade ainda estava sendo calibrada — um job automático rodando contra um `K` ainda em teste era o problema, não o pg_cron em si. Esse motivo caducou com `v2` promovido e validado; o veto foi levantado pelo próprio usuário depois disso, e só então a extensão foi ativada de propósito. Se `pg_cron` aparecer ativo depois de ter sido vetado numa sessão anterior, não é drift — é uma decisão revisitada e revertida depois que a condição que a motivava deixou de existir.

**UI: três estados via `compatEstado()`, não binário null/not-null**: `sem_dado` (`n_comum=0`) não mostra número algum. `normal` (`n_comum>=15`) mostra o `pct` real com cor, calibrada pra faixa real de v2 (não as faixas 80/60/40 da fórmula antiga, que deixariam quase todo mundo amarelo). `baixo` (`n_comum` 1–14) mostra **`n_comum/15` como progresso, não como percentual**, muted, sem cor de faixa, mais uma barra de progresso fina e "ainda conhecendo o gosto de {Nome}" — um `%` real foi tentado primeiro e descartado: com `n_comum=12` e `K=15`, só 44% do peso de `r_ajustado` é sinal real, o resto é a média do grupo, e um `%` muted ainda não resolve isso, porque o número é lido antes de a muting ser percebida. O "ver detalhes" expandível por par mantém seu próprio cálculo por filme ao vivo — `compatibilidade` só guarda o agregado, nunca "quais filmes" — mas os blocos agregados do detalhe (afinidade por gênero, evolução da afinidade, gênero divisor) ficam escondidos pra pares `baixo`/`sem_dado`, já que um `%` ao lado de "ainda não dá pra comparar" se contradiz na mesma tela; blocos factuais sobre filmes específicos (nota máxima em comum, ambos amaram, maior divergência, só vocês dois assistiram, "{Nome} amou e você não viu") ficam pra todo estado, já que um fato sobre N filmes compartilhados é verdade independente da confiança no agregado.

**Inconsistência conhecida e aceita, não descuido**: a matemática interna do detalhe por par ainda é diferença bruta de nota (pré-v2), enquanto o `pct` do placar é baseado em `desvio_pessoal` (v2) — duas fórmulas diferentes na mesma tela de propósito, já que corrigir isso significaria carregar `v_avaliacao_comparativo` por par em vez de por perfil sob demanda, desfazendo o limite deliberado de payload da camada de leitura de conquistas (~356KB evitados).

### Segurança: SECURITY DEFINER e RPC pública

**Regra**: toda função `SECURITY DEFINER` nasce exposta via RPC. A anon key é pública — embutida em `index.html`, servida estática pelo GitHub Pages, visível a qualquer um que abra o site — então por padrão Postgres/PostgREST deixam `EXECUTE` liberado pra `public` (que inclui `anon` e `authenticated`) em toda função nova. Numa função comum isso é inofensivo porque a RLS da tabela ainda barra a escrita; numa `SECURITY DEFINER` (que existe justamente pra *contornar* a RLS de uma tabela sem policy de escrita, como `conquistas` e `compatibilidade`) isso reabre exatamente o buraco que a função foi criada pra evitar de outro jeito. **Revogar `EXECUTE` de `public`/`anon`/`authenticated` é parte de criar a função, não um passo de segurança separado pra lembrar depois** — toda `create function ... security definer` vem na mesma migração com:
```sql
revoke execute on function public.<nome>(<args>) from public, anon, authenticated;
alter function public.<nome>(<args>) set search_path = public, pg_temp;
```
(`search_path` fixo pelo mesmo motivo — nasce junto, não é corrigido depois num scan de advisories.)

Aplicado a `recalcular_compatibilidade()` e à sua wrapper de gatilho `_trg_recalcular_compatibilidade()`: ambas `SECURITY DEFINER`, `search_path` fixo, `EXECUTE` revogado de `public`/`anon`/`authenticated` (só `postgres`/`service_role`) — confirmado por leitura direta de `pg_proc`. `get_advisors(type='security')` rodado depois de criar os gatilhos de conquistas e compatibilidade: nada além do `auth_leaked_password_protection` já conhecido (ver Pendência abaixo).

Views (`v_avaliacao_comparativo`, `v_filme_stats`) usam `security_invoker=true` — sem isso, uma view roda com o privilégio de quem criou, não de quem consulta, o padrão antigo do Postgres pra views sem essa opção declarada. Seguro porque `avaliacoes`/`filmes` já abrem `SELECT` pra `public`; `usuarios` abre só pra `authenticated`, o mesmo papel que qualquer sessão logada real já usa. Validado com sessão `authenticated` real no app (celular, logado) depois da migração — Estatísticas, Afinidades e Conquistas, as três telas que dependem dessas views, carregaram normalmente.

**Regra irmã, mesmo padrão**: toda policy de escrita nasce com o escopo mais largo possível se ninguém restringir — igual ao `EXECUTE` de uma `SECURITY DEFINER` acima. `perfis.perfil_write` era `FOR ALL TO public`: a escrita só era barrada pela condição (`auth.uid()` é sempre `NULL` pra quem só tem a anon key, sem sessão), nunca pelo escopo de role. **Escopo por comando (`FOR INSERT`/`UPDATE`/`DELETE`, nunca `ALL` por hábito) e por role (`TO authenticated`, nunca `public` por padrão) é parte de criar a policy, não um passo separado pra lembrar depois** — se a condição um dia mudar ou tiver um bug, o role é a segunda barreira que sobra. Este é o terceiro caso do mesmo padrão de escopo-largo-demais nesta leva (função `SECURITY DEFINER` exposta via RPC, `compatibilidade` sem RLS nenhuma, e agora esta policy `TO public`) — é o que justifica a regra existir, não coincidência.

**Pendência separada, fora de qualquer migração**: `auth_leaked_password_protection` está desabilitado no Supabase Auth (não checa senhas comprometidas via HaveIBeenPwned). É configuração de Auth, não schema — decidir e aplicar quando fizer sentido, sem misturar com migração SQL.

### Auth & admin

Login is Supabase Auth email/password (`supa.auth.signInWithPassword`/`signUp`/`resetPasswordForEmail`). After a successful auth, `onLogin()` does a live `usuarios` lookup by email — if it comes back empty the account exists but isn't a recognized member yet (shown as a distinct message, app doesn't load). There's no roles table; admin access is a single hardcoded email check (`ADMIN_EMAIL`) gating the admin panel UI and its Supabase writes (which are enforced by RLS server-side too, not just hidden client-side).

### Notifications

Push (FCM) is wired through a separate Google Apps Script deployment (`apps_script_notificacoes.js`, not part of the `index.html` bundle — see the header comment in that file for the manual deploy steps) that the app calls via a plain `fetch` to a Web App URL (`APPS_SCRIPT_URL`), since a static GitHub Pages site can't send push itself.

### External APIs used client-side

TMDB (movie metadata/posters, catalog search-and-add autocomplete), plus IMDb/Rotten Tomatoes ratings and "where to watch" lookups shown on the film detail panel. All API keys are embedded directly in `index.html` (anon/public-scoped keys — there is no server, so there's nowhere else for them to live); this is intentional, not an oversight.

## Working conventions established in this repo

- Commits are small and scoped to one logical change each; stage `index.html` (and only the specific other files actually touched) explicitly rather than `git add -A`, since untracked scratch/export files (`*.csv`, `backups/`) are gitignored but other stray local files may not be.
- Never commit CSV files or anything under `backups/` — both are gitignored on purpose (DB exports/backups are local-only, not repo content). Don't override the ignore for a one-off "just this once".
- Show the diff and wait for explicit approval before committing or pushing.
- **"Show the diff" means paste the literal diff text inline in the chat message, in a code block — for any file (CLAUDE.md, index.html, SQL migrations).** Never say "shown above," never rely on a tool-rendered diff view or file panel — it does not reach the user in this setup, and every time it happens it burns a full round-trip just to get it re-pasted as text.
- **The cycle is four separate steps, in order: diff pasted inline → user approves → commit → push.** Pasting the diff and committing in the same turn is not "showing the diff," even when the diff is small (a one-line fix) or obviously correct — commit only after the user's own message approves it, not right after your own message that includes the diff. Push is its own separate ask on top of that, same as before.
